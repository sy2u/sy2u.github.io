本文依据所提供的 PDF 作 AI 辅助阅读整理，未独立复现实验。

这篇论文研究GPU 内部的计算拓扑和访存差异如何影响细粒度调度。随着芯片变大、内部互连变复杂，以及多芯粒 GPU 的出现，SM 所在的位置、哪些 TPC 被禁用、数据落在哪个内存分区，都会影响最终性能。调度器需要结合这些信息，判断分给任务的资源能提供多少计算能力和访存带宽。

全文沿着两条线推进：先逆向测出计算拓扑的不对称和访存的非均匀性，再用整卡 kernel、同一应用的 prefill/decode 并行、多租户共置三个场景，说明调度器为什么需要知道资源的身份与位置。作者分别为这三个场景构建原型，验证硬件差异对性能的影响。

§1–4 背景与动机：SM 数量为什么不够描述一块 GPU

PDF p. 1–3

先看清 GPU 的两套组织

读图：图 1 的上半部分是计算层次：GPU 包含多个 GPC，每个 GPC 又包含多个 TPC，本文讨论的 NVIDIA GPU 每个 TPC 包含两个 SM。下半部分是访存路径：SM 通过互连访问分区化的 L2 和 HBM。计算层次决定哪些 SM 能共同执行一个 cluster；访存路径决定这些 SM 访问各内存分区的代价。调度器需要同时考虑这两类约束。

  • Floorsweeping：为容纳制造缺陷等因素，芯片会禁用部分 TPC。完整设计中的资源数与产品实际启用的资源数因此不同。例如 GH100 完整设计有 144 个 SM，论文的 H200 启用 132 个；B200 的完整配置为 160 个，实际启用 148 个。
  • Thread Block Cluster：一组需要协作的 thread blocks。论文利用其共同落在一个 GPC 内的约束，探测 SM 的归属；较大的 cluster 也会放大资源碎片问题。
  • NUMA：同一个逻辑 GPU 内，某个 SM 访问本地内存分区和远端分区的成本不同。这些差异存在于同一逻辑设备内部。
  • Green Context / MPS / MIG：不同方式的 GPU 资源划分或共享机制。本文关心的是，它们实际交付了哪些 SM，以及这些 SM 的 cluster 能力和内存亲和性。

禁用单元之后，逻辑 SM ID 会重新组织，因此不能只根据一个连续编号区间，推断其中的 SM 在物理上属于哪个 GPC。即使型号相同，不同芯片的 floorsweeping 位置也可能不同。

GPU 会将数据分布到不同的内存分区，而 SM 访问这些分区的代价并不相同：访问本地分区较快，访问远端分区则需要经过额外的互连。因此，调度时除了考虑分配多少个 SM，还需要考虑这些 SM 与所访问数据的位置关系。

已有的 MLOPart 等接口支持 NUMA 相关的资源管理。本文进一步研究具体芯片的 SM 拓扑、SM—内存亲和性，以及调度和分配怎样共同利用这些信息。

§5 计算不对称：如何还原每个 SM 所在的 GPC

PDF p. 3–6；附录 B，PDF p. 13

§5.1 两阶段探测：先用 cluster 分组，再用共享带宽补全

第一阶段：作者使用 cudaLaunchKernelEx 启动大小为 3–8 的 clusters，并在 kernel 中记录 %smid。同一个 cluster 内的 SM 必须来自同一个 GPC，因此反复采样可以建立 SM 的分组关系。

第一阶段只能识别参与这些 cluster 的 SM。在论文的一块 H200 上，编号 0–123 的 SM 可以通过这种方式归组，而 124–131 不出现在大小大于 2 的 cluster 中。作者把前一类叫 normal SM，后一类叫 random SM。这里的 random 指这些逻辑 SM ID 对应的 GPC 归属随芯片的 floorsweeping 结果而变化。对一颗给定芯片，SM 的物理位置固定；random SM 的数量则取决于该芯片的配置。

第二阶段：图 2 利用共享互连的带宽瓶颈补齐遗漏。把工作集设置得大于 L1、小于 L2，再逐步增加参与访问的 SM。如果这些 SM 来自同一个 GPC，它们会共享 Xbar 带宽，聚合吞吐较早饱和；若来自不同 GPC，带宽还能继续增长。论文在 H200 超过约 6 个 SM、B200 超过约 16 个 SM 后观察到明显区别。

因此，可以让一个待归组的 TPC 与某个已知 GPC 的 SM 一起运行：如果新增的带宽很少，就支持“它们共享同一 GPC 互连”的判断。作者报告，两阶段方法在每块 GPU 上耗时不到一分钟，并在测试设备上与 nvdebug 的映射结果完全一致。

§5.2 同型号芯片的拓扑，也可能不同

读图：图 3 把 normal TPC、random TPC 和被禁用的 TPC 放回 GPC 中。应关注三个问题：每个 GPC 剩多少可用 SM、哪些 SM 能参加大 cluster、两侧内存分区分别靠近多少 SM。图中的左右排列示意内存分区的拓扑关系；分区编号与实际芯片上的左右位置可以互换。

在 28 块 H200 中，最常见的配置是 6 个 GPC 各有 16 个 SM、另外 2 个各有 18 个，出现于 23 块卡。其余芯片存在更不均匀的组合，极端情况下一个 GPC 只有 10 个 SM，另一些有 18 个。论文跨设备分析还发现，同一 GPU 内 GPC 的 SM 数量差距可达到 10 个。

大 cluster 的调度还受到 SM 类型的限制。作者在一块每个 GPC 至少有 16 个 SM 的 H200 上发现，其中一个 GPC 包含 8 个 normal SM 和 8 个 random SM；这 8 个 random SM 无法承接大于 2 的 cluster。评估 cluster 可用容量时，需要同时记录 GPC 的 SM 数量及其 cluster 兼容性。这一结论描述的是论文测试的硬件与软件栈上的行为。

§5.3 资源划分接口交付的 SM，存在隐藏差异

论文使用默认模式的 Green Context：分配以 GPC 对齐的 8-SM 块为单位，跨 GPC 铺开。前面的 context 优先拿到 normal SM，最后一个 context 则可能包含 random SM。结果是，即便给租户相近的 SM 配额，较晚创建的 context 也可能更不适合大 cluster。

附录 B 还讨论两种不同模式：IGNORE_SM_COSCHEDULING 可以更独立地分配 TPC，但不支持大于 2 的 cluster；MAX_POTENTIAL_CLUSTER_SIZE 更强调把 GPC 对齐的资源集中起来。正文实验均采用前述默认模式。

MIG 则使用固定的实例配置。论文给出的 H200 例子中，4g.71GB 与 3g.71GB 分别提供 64 和 60 个 SM，合计 124 个，少于芯片启用的 132 个。为满足跨芯片一致的 profile，部分本来可用的 SM 也可能无法分配给这些实例。作者对 B200 某些 profile 数量给出了制造约束方面的可能解释，但这部分应保留为解释性推测。

§6 访存不对称：同一地址，从不同 SM 访问会怎样

PDF p. 6–7；图 8，PDF p. 8；附录 C–D，PDF p. 13–14

§6.1 延迟的两个峰，对应本地与远端分区

为了测 HBM，作者让固定 SM 上的单个线程随机访问约十万个地址，先用 discard.global.L2 排除 L2 命中，再用绕过 L1 的 ld.cg 读取，并以 clock64 计时。图 4 中明显分离的峰，说明访存路径存在不同的成本。

L2 测试先从某个 SM 把数据加载到它的本地 L2，再分别从本地或不同亲和性的 SM 发起第二次访问。这样尽量把 HBM 成本与 L2 分区间的访问成本分开。图 5 显示，从不同亲和性的 SM 访问同一个 L2 分区，会得到不同的延迟。

访问对象H200：本地 → 远端B200：本地 → 远端
HBM 延迟约 490 → 655 cycles（+34%）约 552 → 920 cycles（+67%）
L2 延迟约 309 → 466 cycles（+51%）约 364 → 725 cycles（接近 2 倍）

这些数值是论文微基准测得的时钟周期。换算为纳秒或比较跨代际的绝对时间时，需要结合各自的时钟频率。B200 的本地 HBM 峰还有细分迹象，作者据此推测 die 内可能仍有更细的延迟差异；但峰有重叠，未能据此清楚分离边界，而带宽和容量测试在这一层表现得更像统一分区。

对每个 SM 重复相同访问，可以建立 SM 到内存分区的亲和关系。两边的 SM 数量未必相等：论文观察到 H200 两个分区之间最多相差 12 个 SM，B200 最多相差 8 个。因此即使把数据平均切成两份，也可能产生计算负载不均。

地址怎样选择内存分区：XOR hash 与 4 KB 交错

作者逐位翻转物理地址并观察延迟类别，识别参与分区选择的地址位。H200 和 B200 各有 16 个参与位，H100 PCIe 为 14 个；最小参与位是 bit 12。这意味着地址按 4 KB 的分区交错粒度映射。虚拟内存页大小由地址翻译机制另行决定，可以采用更大的页面。

抽象地，可以把分区号写成 partition = parity(physical_address & MASK)：先保留掩码指定的位，再计算这些位中 1 的个数的奇偶性。不同 SKU 的掩码不一定相同。图 6 展示 B200 的位选择关系；其他设备需使用对应的掩码。作者报告，识别 hash 大约需要 10 秒；可选的整个 80 GB 地址空间验证约需 15 分钟。

§6.2 有效 L2 容量为何小于标称容量

读图：图 7 扫描工作集大小，观察带宽何时从 L2 水平跌落。H200 标称 60 MB L2，在这项测试中约 39.5 MB 就出现转折；B200 标称 126 MB，对应转折约为 81.5 MB。两者都只有标称容量的约 65%。这些转折反映该访问模式下可利用的 L2 容量。后续实验通过分区访问和缓存副本，解释它与标称物理容量的差距。

进一步只访问某个分区的本地数据，图 8 显示 H200 和 B200 的单分区 L2 容量分别约为 30 MB 和 62 MB。远端访问则受连接两个分区的 LTC fabric 限制，跨分区互连成为吞吐瓶颈。图中的容量数值由带宽曲线的转折位置估计。

作者又设计了失效与重新加载实验：本地 SM 读一个归属远端分区的地址，随后由远端 SM 执行失效操作，再由本地 SM 重读。后一次访问仍呈现约 310 cycles（H200）或 360 cycles（B200）的本地 L2 延迟。这支持一个解释：远端取回的数据也会被复制到请求者的本地 L2。

于是同一份数据可能占据两个分区的容量，减少可容纳的唯一数据量，并增加相互驱逐。该实验支持跨分区复制与一致性行为的判断，但论文没有完整逆向所有 coherence 状态和协议细节。

§7.1 整卡 kernel：让数据与执行它的 SM 靠在一起

整卡 kernel 的各个 SM 也可能访问远端数据，因此同样会受到 NUMA 影响。作者先提供两种定向内存分配方式，再改写工作分配。

间接分配：保留大页映射，分配物理连续的区域，然后在 kernel 内构造两个逻辑视图，分别只访问目标分区的 4 KB 页面。由于 bit 12 参与 XOR，按偶数物理页号对齐的相邻页面 (2j, 2j+1) 恰好分属两个分区。图 9 的两条逻辑序列就来自同一段物理区域。

附录 E 给出的选择规则，可以写成：

page_offset = 2j + (parity((page_start + 2j) & MASK) XOR P)
  • j：某个分区逻辑视图内的页编号。
  • page_start：分配区域的起始物理页号，须满足页面配对的对齐条件。
  • MASK：换算到 4 KB 页号单位的硬件分区掩码。
  • P：目标分区，取 0 或 1。
  • page_offset：相对分配起点的页偏移，页内字节偏移保持不变。

直观上，先检查一对页面中的第一页是否属于目标分区：属于就取它，不属于就加 1，取另一页。每次地址转换只需固定数量的位运算，无需查表。对由完整页面对组成的 S 字节区域，每个分区的逻辑视图容量为 S/2。

实现条件很重要：这种方法需要修改驱动，以提供物理连续的内存分配及其物理起始地址。作者曾尝试直接使用 4 KB 虚拟内存页，但 TLB 压力使访存型 kernel 性能下降，因此最终保留大页，在页内部进行 4 KB 粒度的选择。

直接分配：另一种方法修改驱动中与 MLOPart 相关的代码，直接指定目标 NUMA 分区，省掉 kernel 内的地址重映射。论文将其适用范围限定在 Blackwell 及更新、具有所需支持的 GPU。

随后，作者把 kernel 转成 persistent thread blocks（PTB）：每个 SM 固定一个 block，以循环领取任务。知道 block 的 SM ID 后，就能把它分配到本地数据对应的任务；如果两侧 SM 数不等，还要按 SM 数量比例切分工作，使两侧的任务量匹配各自的计算容量。

读图：图 10 每个点对应不同工作集和配置，横向虚线为原始实现的 1×。测试涵盖 MHA、GQA、MLA 的 prefill/decode，以及 GroupGEMM；H200 与 B200 的两个分区在这组实验中分别为 66/66 和 74/74 个 SM。最好的结果是 B200 GroupGEMM 约 1.22×，但小工作集等配置也存在低于 1× 的点。

减少远端访问的收益需要覆盖新增的执行开销。PTB 的启动、读取 SM ID、软件地址重映射都会增加开销；如果原始任务很短，或额外算术本身成为负担，收益就可能被吃掉。H200 的 GroupGEMM 尤其受到重映射指令的影响。

图 11(a) 用 PC sampling 观察指令开销：H200 GroupGEMM 中，Selected 状态（warp 发射了一条指令）的样本比例从约 25.96% 增至 35.04%；MHA prefill 则从 13.92% 增至 14.71%。这些比例表示采样中 warp 发射指令的占比。它们用于分析新增地址计算的影响；实际耗时变化需结合运行时间测量。

图 11(b) 则在两侧为 70/78 个 SM 的 B200 上测试 MLA decode。只追求本地性、却忽略计算容量比例时，部分配置性能降到约 0.78×；把任务按拓扑重新平衡后，最高达到约 1.10×。这说明局部性优化还必须同时解决负载均衡。

§7.2 应用内并行：prefill 与 decode 怎样共享 GPU

一个 LLM 服务可以让 prefill 与 decode 并行。两者共享权重和 KV，同时各自拥有私有中间状态。对于无法任意修改的 kernel，把所有地址访问都换成软件重映射并不现实。

作者在 MIG 的基础上修改驱动，让一个实例能够映射另一个实例的内存。图 12 表示这种跨实例映射：私有数据放在各自的本地分区，共享权重和 KV 则均匀分布在两边，以 64 KB 映射粒度交错。这里的 64 KB 是该实现共享内存映射的粒度，与前面的硬件 4 KB 分区 hash 粒度不同。跨实例映射依赖本文对驱动的修改。

测试使用 mini-SGLang 与 Qwen3-8B。H200 分给 prefill/decode 的 SM 数为 64/56，B200 为 64/64；prefill 的 batch 为 4、序列长度为 4K，decode 的 batch 为 128、平均 KV 长度为 512。作者比较：

  • CA：cluster-compatible、NUMA-agnostic；使用 Green Context 与 MPS，满足大 cluster 的计算布局，但不利用内存亲和性。
  • CM：cluster-mismatched；内存策略与 CA 相同，但 SM 集合不能完全满足 cluster size 8 的要求。
  • AN：asymmetry-aware NUMA placement；利用 MIG 和上述内存布局，同时满足 cluster 兼容性与 NUMA 放置。

读图：先看 standalone：CA 与 AN 单独运行的吞吐接近，说明在这些测试下方案没有明显的独立运行开销。再看 overlap：相对 CA，AN 的 decode 吞吐在 H200 上提高 14.3%，B200 上提高 10.4%；prefill 更偏计算密集，收益较小。

CM 则揭示另一条路径：B200 decode 吞吐相对 CA 下降 18.9%，即使内存策略没有变，cluster 不匹配也会造成损失。H200 的影响较弱，论文将其联系到实际多数 kernel 使用大小为 2 的 cluster。这些收益对应本节列出的模型、batch 和 kernel 配置。

§7.3 应用间共置：先申请和后申请，得到的资源等价吗

这组实验让应用 A 使用 cluster size 2、4 或 8，应用 B 固定使用 size 2 的 GEMM，再交换二者申请 Green Context 的顺序。图 14 展示了两次分配实际拿到的 SM：最后的 context 更容易包含 random SM，也可能留下不适合较大 cluster 的 GPC 内碎片。

读图：图 15 中 A 先申请与后申请的吞吐差，在 cluster size 4 时约为 H200 1.18×、B200 1.11×；size 8 时约为 H200 1.18×、B200 1.33×。这组实验实际分配的 SM 数为：H200 为先分 64、后分 68，B200 为先分 72、后分 76。后分者甚至拿到更多 SM，仍可能更慢。

图 16 给出一个很直观的例子：B200 的一个完整 GPC 有 20 个 SM，若 B 占去 8 个，就还剩 12 个。对于 size 4，12 个 SM 可以形成 3 组；对于 size 8，只能形成 1 组，另外 4 个无法凑成第二组。再叠加 random SM 的限制，配额表面上“足够”，实际也可能用不满。

【帮助理解的简化模型】如果把每个 block 占一个 SM、同 GPC 内按 cluster 大小 c 成组作为假设，可用容量近似写成 Σ_g c × floor(n_g / c)，其中 n_g 是该 GPC 内剩余且符合 cluster 条件的 SM 数。这个式子只解释整组分配造成的碎片。完整的 occupancy 分析还需纳入寄存器、共享内存等资源限制。

因此，论文对多租户调度的建议是：把租户的 cluster 要求与实际 SM 拓扑纳入分配，同时利用较小 cluster 的任务填补碎片；只按 SM 数量或申请先后分资源，不足以保证性能公平。

§8–9 讨论与结论：哪些发现可以推广

PDF p. 12

本文最稳妥的结论是：GPU 内部的物理不对称，已经能够影响软件层的细粒度调度。对整卡 kernel，优化要同时考虑本地性、地址计算成本和负载平衡；对应用内并行，私有状态与共享状态需要不同放置策略；对多租户，cluster 兼容性使“数量相同”无法自动等价于“能力相同”。

作者也讨论 GPU 模拟器的影响：如果模型把所有 SM 视为对称、把 L2/HBM 视为均匀可达，就可能遗漏这些现象。作者将把测得的拓扑与延迟加入模拟器列为后续研究方向。

结论的适用范围需要与测量边界对应：SM 的具体编号、地址 hash、Green Context 行为依赖设备和软件栈；微基准的延迟与有效容量依赖访问模式；性能收益依赖 kernel、工作集和并发配置。论文提供了测量这些因素的方法，使调度器能够根据当前设备的拓扑和访存特性分配资源。

附录 A H100 PCIe：同样的方法，得到不同的分组

图 17 是 H100 PCIe 的还原结果，共 114 个启用 SM。它的 GPC 数量、normal/random SM 的组合以及被禁用的区域，与前面的 H200/B200 不同。这个例子强化了一个工程含义：调度前应测出当前设备的拓扑。图中的结果适用于这块 H100 PCIe。

附录 C–E 三层映射不要混淆

PDF p. 13–14

图 18 可以作为全文的访存总图。从一个 kernel 的指针开始，至少要区分：

  1. 虚拟地址 → 物理地址：由页表与 TLB 参与，论文的最终方案保留大页以降低翻译压力。
  2. 物理地址 → NUMA 分区：通过本文逆向的 XOR hash，最低参与位对应 4 KB 交错粒度。
  3. 分区内部 → L2 slice / HBM channel：需要更细的地址映射规则，本文重点分析到 NUMA 分区这一层。

当目标地址属于远端分区，请求要经过 LTC fabric；返回的数据还可能在本地 L2 留下副本。因此“远端带宽瓶颈”和“有效 L2 容量减少”有共同的跨分区访问背景，分别体现为吞吐上限和可容纳的唯一数据量，需要各自测量。

附录 G AMD MI300X：计算组织不同，访存仍然不均匀

PDF p. 15–16

AMD MI300X 提供了一个对照。论文描述的组织为 8 个 XCD、4 个 AID，每个 AID 对应 2 个 XCD。每个 XCD 完整设计有 40 个 CU，启用 38 个；不像上述 NVIDIA 实验，它没有同样的硬件 thread-block-cluster 机制，因此不能直接照搬 normal/random SM 的调度结论。

每个 XCD 有 4 MB L2，每个 AID 有 64 MB Infinity Cache，并连接两个 HBM3 堆栈。图中的 Infinity Fabric 示意计算芯粒与 I/O 芯粒之间的连接关系。虽然计算资源更均匀，访存亲和性仍然存在。

作者在 32 GiB 空间中采样一百万个按 128 字节对齐的随机地址，从各 XCD 测量，绕过 L1/L2 并处理 Infinity Cache 的缓存影响。每个地址做多次测量并保留最小值。结果显示 XCD 按 {0,1}、{2,3}、{4,5}、{6,7} 形成四组亲和关系，各对应约四分之一的采样地址。

图 20 从 XCD 0 出发，本地、邻近、对侧三类地址的平均访问延迟分别约为 707、817、926 cycles。这里的“邻近”和“对侧”是作者根据延迟推断的类别，实际互连跳数仍待验证。三条分布各自归一化，用于比较各类地址内部的延迟分布；各类地址在整个采样空间中的占比需另行统计。

读完后值得留下的几个问题

  • 拓扑何时重新探测？本文展示了快速探测方法，但长期系统还需确定驱动变化、资源模式切换后哪些信息需要刷新。
  • 什么时候值得定向放置？远端流量减少的收益，要与重映射指令、PTB 和负载不均的代价一起算；图 10–11 已说明局部性提高并不必然加速。
  • 共享数据该复制、交错还是集中？本文采用私有本地、共享交错的策略；其他访问比例、写入行为与容量压力下，最合适的选择仍需测量。
  • 公平性该按什么衡量？可以把满足租户 cluster 条件的有效计算资源及内存亲和性纳入公平性指标。这是由实验引出的后续设计问题。

一句话记忆：这篇论文让调度器从“分多少 SM、多少显存”，进一步走向“分哪些 SM、数据放在哪里，以及这些资源能否一起高效工作”。
