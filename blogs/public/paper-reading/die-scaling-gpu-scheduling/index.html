本文依据所提供的 PDF 作 AI 辅助阅读整理，未独立复现实验。

这篇论文的核心发现是：分给任务的 SM 位于哪里、能与哪些 SM 协作，会直接影响这份计算资源的实际性能。在测试的 H200、B200 上，部分 SM 无法参与较大的 thread block cluster，同一 GPC 内剩余的 SM 也可能因凑不齐一个 cluster 而闲置；SM 访问远端内存分区时，还会付出更高的延迟和跨分区带宽代价。因此，调度器需要同时考虑 SM 的分组、cluster 要求与数据位置。

数据放到本地之后，工作量还要与各分区的计算能力匹配。论文测到一块 B200 的两个内存分区分别对应 70 和 78 个 SM。如果两侧各承担一半工作，SM 较少的一侧就会拖慢整个任务。按 SM 数量比例分配数据与任务，才能同时获得本地访问和负载均衡的收益。

§1–4 必要背景：计算分组与内存分区

PDF p. 1–3

图 1 上半部分是计算层次：GPU 包含多个 GPC，每个 GPC 包含多个 TPC，本文的 NVIDIA GPU 每个 TPC 有两个 SM。Thread Block Cluster 是一组协作的 thread blocks，需要落在同一个 GPC 中。制造时禁用部分 TPC 的做法称为 floorsweeping，它会改变各 GPC 的可用资源数；逻辑 SM 编号也会重新组织，因此需要测出编号对应的物理分组。

下半部分是访存路径：L2 和 HBM 分成不同的内存亲和分区。一个 SM 访问本地分区较快，访问远端分区要经过额外互连，这就是本文讨论的 GPU 内部 NUMA。后文分别测量“哪些 SM 属于同一 GPC”和“哪些 SM 靠近同一内存分区”。

PDF p. 3–5

§5.1 两阶段探测：先用 cluster 分组，再用共享带宽补全

第一阶段：记录哪些 SM 曾共同执行一个 cluster。作者使用 cudaLaunchKernelEx 启动包含 3–8 个 thread blocks 的 cluster，让各个 block 读取 %smid，记录自己运行在哪个 SM 上。同一 cluster 的 blocks 必须位于同一个 GPC，因此这次记录到的 SM 可以归为同一组。

重复采样后，还可以通过共同出现的 SM 合并分组。例如，一次记录到 {a, b, c}，另一次记录到 {c, d, e}，两次都有 SM c，就能判断 a、b、c、d、e 属于同一个 GPC。在测试的一块 H200 上，这种方法确定了 SM 0–123 的 GPC 归属。SM 124–131 未出现在 size 3–8 的 cluster 中，作者随后通过共享互连上的带宽争用确定它们的归属。

作者将这些 SM 分为 normal SM 和 random SM。normal SM 的逻辑编号遵循该架构预先定义的 GPC 映射：哪些 SM ID 属于同一个 GPC，有固定的分组关系。random SM 的编号与 GPC 的对应关系则取决于每颗芯片具体禁用了哪些 TPC；同一个 random SM ID 在不同芯片上可能属于不同的 GPC，因此需要逐卡测量。前面的 cluster 探测识别了 normal SM 的分组，接下来的带宽探测补全 random SM 的归属。

第二阶段：作者让 SM 反复读取大于 L1、小于 L2 的工作集，测量 L2 聚合带宽。图 2 中，H200 超过约 6 个 SM 后，同 GPC 的带宽增长明显慢于跨 GPC；B200 在 2–16 个 SM 时两组几乎重合，到 18–20 个 SM 才拉开差距，20 个 SM 时约为 4.4 与 4.9 TB/s。参与访问的 SM 较少时，单个 GPC 的交叉互连（Xbar）足以承载流量；SM 增多后，共享这条互连的带宽限制才显现。因此，这种探测需要用足够多的已知 SM 产生带宽争用。

论文把连续编号的两个 random SM 作为同一 TPC 的一对来测试；此时已知的是 TPC 内的配对，待确定的是这个 TPC 属于哪个 GPC。原文未说明配对关系如何验证，也未报告 size 2 的探测结果。随后，作者让这一对 SM 依次与各个已知 GPC 的 SM 集合一起运行，比较加入前后的聚合带宽。如果增量小于一个 TPC 单独能提供的带宽，就表明它与该组 SM 争用同一条 GPC 互连，据此确定归属。作者报告，两阶段方法在每块 GPU 上耗时不到一分钟，所得映射在测试设备上与 nvdebug 完全一致。

§5.2 同型号芯片的拓扑，也可能不同

读图：图 3 把 normal TPC、random TPC 和被禁用的 TPC 放回 GPC 中。应关注三个问题：每个 GPC 剩多少可用 SM、哪些 SM 能参加大 cluster、两侧内存分区分别靠近多少 SM。

在 28 块 H200 中，最常见的配置是 6 个 GPC 各有 16 个 SM、另外 2 个各有 18 个，出现于 23 块卡。其余芯片存在更不均匀的组合，极端情况下一个 GPC 只有 10 个 SM，另一些有 18 个。

大 cluster 的调度还受到 SM 类型的限制。作者在一块每个 GPC 至少有 16 个 SM 的 H200 上发现，其中一个 GPC 包含 8 个 normal SM 和 8 个 random SM；这 8 个 random SM 无法承接大于 2 的 cluster。评估 cluster 可用容量时，需要同时记录 GPC 的 SM 数量及其 cluster 兼容性。这一结论描述的是论文测试的硬件与软件栈上的行为。

§6.1 延迟的两个峰，对应本地与远端分区

为了测 HBM，作者让固定 SM 上的单个线程随机访问约十万个地址，对每个地址先用 discard.global.L2 使 L2 缓存行失效，再用绕过 L1 的 ld.cg 读取，并以 clock64 计时。这两步使被计时的访问到达 HBM，避免把缓存命中误当成较快的内存访问。图 4 将这些延迟画成分布，本地与远端路径形成两个主要的峰。

L2 测试先选一个归属 SM s 本地分区的地址 p，用 s 将它读入 L2。测本地延迟时，由 s 再读一次 p；测远端延迟时，改由另一分区的 SM s′ 读取同一个 p。预热和计时访问都使用 ld.cg 绕过 L1。这样，第二次访问的数据已在 L2 中，两组测量改变的是请求者与该 L2 分区的位置关系。图 5 展示了由此得到的延迟差。

访问对象H200：本地 → 远端B200：本地 → 远端
HBM 延迟约 490 → 655 cycles（+34%）约 552 → 920 cycles（+67%）
L2 延迟约 309 → 466 cycles（+51%）约 364 → 725 cycles（接近 2 倍）

这些数值是论文微基准测得的时钟周期。换算为纳秒或比较跨代际的绝对时间时，需要结合各自的时钟频率。

对每个 SM 重复相同访问，可以建立 SM 到内存分区的亲和关系。两边的 SM 数量未必相等：论文观察到 H200 两个分区之间最多相差 12 个 SM，B200 最多相差 8 个。因此即使把数据平均切成两份，也可能产生计算负载不均。

地址怎样选择内存分区：XOR hash 与 4 KB 交错

前面的延迟分类还可以用来识别地址映射：固定发起访问的 SM，每次只翻转物理地址的一位，再测 HBM 延迟。如果地址从本地延迟类别切换到远端类别，或反过来，就说明这一位参与了分区选择。论文由此在 H200 和 B200 上分别找到 16 个参与位。

最低参与位是 bit 12。一个对齐的 4 KB 区域内，变化的只有 bit 0–11，因此区域内所有地址都属于同一分区；改变 bit 12 会切换分区。这给出了 4 KB 的硬件分区粒度。页表负责的虚拟地址翻译可以使用更大的页面，后面的分配方法正是利用了这两个粒度的区别。

抽象地，可以把分区号写成 partition = parity(physical_address & MASK)：先保留掩码指定的位，再计算这些位中 1 的个数的奇偶性。不同 GPU 型号的分区掩码可能不同。图 6 展示 B200 的位选择关系；其他设备需使用对应的掩码。

§6.2 有效 L2 容量为何小于标称容量

读图：图 7 使用读密集 kernel，并逐步增大它访问的数据量（工作集）。工作集能装进 L2 时，缓存命中提供较高带宽；装不下时，更多访问落到 HBM，带宽明显下降。曲线的转折位置由此给出有效容量的估计。H200 标称 60 MB L2，在这项测试中约 39.5 MB 就出现转折；B200 标称 126 MB，对应转折约为 81.5 MB。两者都只有标称容量的约 65%。这些转折反映该访问模式下可利用的 L2 容量。后续实验通过分区访问和缓存副本，解释它与标称物理容量的差距。

为了将两侧容量分开测量，作者利用刚刚还原的 hash，把连续内存区域中的 4 KB 页面按分区分类，再限制 kernel 只读取本地页面或远端页面，重新扫描工作集大小。图 8 显示 H200 和 B200 的单分区 L2 容量分别约为 30 MB 和 62 MB。远端访问则受连接两个分区的 LTC fabric 限制，跨分区互连成为吞吐瓶颈。图中的容量数值由带宽曲线的转折位置估计。

远端读取会在请求者的 L2 留下副本吗？作者用三步实验检查这件事：

  1. 本地 SM 读取一个归属远端分区的地址，让跨分区取数实际发生。
  2. 远端 SM 对这个地址执行失效操作，去掉远端的缓存副本。
  3. 本地 SM 再次读取同一地址，并测量延迟。

第三步仍只需约 310 cycles（H200）或 360 cycles（B200），与本地 L2 命中相符。远端副本已被失效，本地仍能快速取到数据，支持第一次跨分区读取在本地 L2 留下了副本的判断。副本会占用容量，并与原有缓存行争用空间，因此跨分区访问会减少缓存可容纳的唯一数据量。这里确认的是复制行为；具体工作负载能利用多少容量，还要通过前面的容量扫描测量。

§7.1 调度实验一：数据本地化后，任务应该怎样分

PDF p. 8–9；附录 E–F，PDF p. 14–15

先把数据放进指定分区

整卡 kernel 的各个 SM 也可能访问远端数据，因此同样会受到 NUMA 影响。作者先提供两种定向内存分配方式，再改写工作分配。

间接分配：保留大页映射，分配物理连续的区域，然后在 kernel 内构造两个逻辑视图，分别只访问目标分区的 4 KB 页面。由于 bit 12 参与 XOR，按偶数物理页号对齐的相邻页面 (2j, 2j+1) 恰好分属两个分区。图 9 的两条逻辑序列就来自同一段物理区域。

附录 E 给出的选择规则，可以写成：

page_offset = 2j + (parity((page_start + 2j) & MASK) XOR P)
  • j：某个分区逻辑视图内的页编号。
  • page_start：分配区域的起始物理页号，须满足页面配对的对齐条件。
  • MASK：换算到 4 KB 页号单位的硬件分区掩码。
  • P：目标分区，取 0 或 1。
  • page_offset：相对分配起点的页偏移，页内字节偏移保持不变。

直观上，先检查一对页面中的第一页是否属于目标分区：属于就取它，不属于就加 1，取另一页。每次地址转换只需固定数量的位运算，无需查表。对由完整页面对组成的 S 字节区域，每个分区的逻辑视图容量为 S/2。

实现条件很重要：这种方法需要修改驱动，以提供物理连续的内存分配及其物理起始地址。作者曾尝试直接使用 4 KB 虚拟内存页，但小页需要更多地址翻译条目，增加了地址翻译缓存（TLB）的压力，使访存型 kernel 性能下降，因此最终保留大页，在页内部进行 4 KB 粒度的选择。

直接分配：另一种方法修改驱动中与 MLOPart 相关的代码，直接指定目标 NUMA 分区，省掉 kernel 内的地址重映射。论文将其适用范围限定在 Blackwell 及更新、具有所需支持的 GPU。

随后，作者把 kernel 转成 persistent thread blocks（PTB）：每个 SM 固定一个 block，以循环领取任务。知道 block 的 SM ID 后，就能把它分配到本地数据对应的任务；如果两侧 SM 数不等，还要按 SM 数量比例切分工作，使两侧的任务量匹配各自的计算容量。

用两个对照检查优化代价

地址计算开销：H200 使用上述间接分配，kernel 每次访问要多做重映射运算。作者将优化后的 MHA prefill（多头注意力的预填充阶段）、GroupGEMM（一个 kernel 内执行多组矩阵乘法）与各自原实现比较，用 PC sampling 观察 warp 发射指令的样本比例，结果见图 11(a)。这一步检查为了减少远端访问，执行端增加了多少指令活动。

图 11(a) 用 PC sampling 观察指令开销：H200 GroupGEMM 中，Selected 状态（warp 发射了一条指令）的样本比例从约 25.96% 增至 35.04%；MHA prefill 则从 13.92% 增至 14.71%。这些比例表示采样中 warp 发射指令的占比。它们用于分析新增地址计算的影响；实际耗时变化需结合运行时间测量。

负载均衡：图 11(b) 在两个分区分别有 70、78 个 SM 的 B200 上运行 MLA decode（多头潜在注意力的逐 token 解码），比较两种都使用本地数据的分配方式：一组忽略 SM 数量差异，另一组按各分区的 SM 数量分配数据和任务。横轴是注意力计算所用的 Key/Value 数据量，即 KV 工作集大小，纵轴是相对原始 kernel 的加速比，1× 表示性能相同。忽略拓扑时，部分配置降到约 0.78×；按拓扑分配后，最高约 1.10×。

这组实验的关键是：两边都访问本地数据，但如果两边各领一半工作，70 个 SM 的一侧就承担了更高的每 SM 负载，整个 kernel 要等它完成。按计算资源比例分配工作，才能同时利用本地性和两侧的计算能力。具体收益随工作集变化，不能只用“远端访问减少了”来预测加速比。

§7.3 调度实验二：同样的申请，分配顺序为何影响性能

PDF p. 10–11

作者用 Green Context 与 MPS 把 SM 分给两个同时运行 GEMM 的应用。A 分别使用大小为 2、4、8 的 cluster，B 始终使用 size 2。对每一种组合，先让 A 拿第一组 SM、B 拿第二组，再交换两者的分配顺序，比较吞吐。这样可以观察同一应用拿到不同 SM 集合之后，性能如何变化。

论文测试的默认 Green Context 模式以 GPC 对齐的 8-SM 块跨 GPC 分配资源，较晚分配的集合会包含前面测出的 random SM。实验实际分配数量为 H200 先分 64、后分 68 个 SM，B200 先分 72、后分 76 个 SM。因此还要结合 cluster 大小，判断这些 SM 中有多少能真正参与执行。

读图：A、B 都使用 size 2 时，两种顺序的吞吐几乎相同；增大 A 的 cluster 后，先申请更快。图 15 中 A 先申请与后申请的吞吐差，在 cluster size 4 时约为 H200 1.18×、B200 1.11×；size 8 时约为 H200 1.18×、B200 1.33×。后分者拿到的 SM 更多，其中的 random SM 却无法用于这些大 cluster，因而可能更慢。

图 16 给出一个很直观的例子：B200 的一个完整 GPC 有 20 个 SM，若 B 占去 8 个，就还剩 12 个。对于 size 4，12 个 SM 可以形成 3 组；对于 size 8，只能形成 1 组，另外 4 个无法凑成第二组。再叠加 random SM 的限制，配额表面上“足够”，实际也可能用不满。

这组对照把申请顺序带来的性能差异，联系到了可检查的硬件条件：哪些 SM 支持当前 cluster、同一 GPC 内的剩余资源能组成多少完整的 cluster。调度器需要按应用的 cluster 要求评估这组 SM 的实际可用容量，再决定把资源分给谁。
